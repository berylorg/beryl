# Live Control

This supplement is normative only for its bounded backend live-control role and is governed by
[design.md](design.md). It does not independently declare engineering rigor.

## Steering

- Public streamed `turn/steer` is available only on an initialized production foreground session with its ordered sink already proven. It accepts exact CAS thread and expected active turn ids, one bounded opaque client-user-message correlation, and the same non-cloneable replayable descriptor source/header as streamed start.
- The request emits only pinned `threadId`, `clientUserMessageId`, ordered `input`, and `expectedTurnId`. It admits no model, reasoning, developer instructions, extra context, metadata, raw JSON, whole collection, or generic mutation overload.
- Every source pass rechecks identity, revision, count, digest, text, paths, detail, and terminal state. The outcome is exact matching success, exact structured rejection, proven nondispatch, or completion unknown after possible dispatch. A returned different turn id is completion-unknown; diagnostic text never creates retry authority. Later user-message lifecycle remains independently ordered and correlated.
- Exact structured `activeTurnNotSteerable` data normalizes only to its closed review or compact verdict. No-active-turn and expected-turn-mismatch remain exact rejections without a machine verdict unless pinned schema/source evidence establishes one; diagnostic text never supplies retry authority.
- Source/revision validation, replay, serialization or masking, cancellation, and concrete transport failure remain distinct typed steering causes under the same monotonic dispatch evidence. Nondispatch proves only no offered request byte, never transience or timer retry; post-dispatch transport, malformed/identity response, or unrecognized remote failure remains completion unknown and retires that session.

## Exact Interruption and Compaction

- `turn/interrupt` is available only on the admitted foreground session owning the exact loaded thread and turn. Durable soft-stop and volatile pre-admission authorizations are noninterchangeable typed families and bind exact runtime, managed-process, loaded-thread, CAS thread, turn, and sole driver identity. An explicit unbind revokes prior authorization.
- Durable authorization carries bounded opaque stop-operation and attempt correlations for local reconciliation, never protocol idempotency keys. Volatile authorization is process-local, non-cloneable, single-use, and valid only after typed pre-writer admission failure or `NotCommitted`; possible durable authority, `Committed`, `Indeterminate`, cancellation after admission, drift, replacement, resumed/request-only session, or restart rejects it.
- The sole foreground driver serializes interruption with polling, approval response, target close, and terminal handoff and proves the caller holds the no-successor operation fence. Empty-turn startup interrupt, hard stop, child/process termination, background cleanup, and managed-process shutdown are not turn control.
- Durable and volatile outcomes separately preserve matching response acceptance, `RejectedBeforeCoreInterrupt`, proven nondispatch, and completion unknown. For pinned `0.146.0`, only correlated `-32600` with absent `data` and handler-local `-32603` submission failure with absent `data` match `RejectedBeforeCoreInterrupt`; this version-scoped matcher never parses message text and proves neither target currency nor terminality. No interruption retries.
- `thread/compact/start` accepts one exact bounded thread id and emits its pinned request shape only. It does not require or imply idleness, attach input, guessed turn id, completion timeout, subscription, provider completion, or backend policy. Its non-idempotent outcome is exact acceptance, source-pinned rejection, nondispatch, or completion unknown; callers already own the foreground subscription and system-owned operation gate.
- Compact start rejects invalid or unloaded thread identity but may accept an active thread; backend acceptance is an empty acknowledgement after core submission, has no turn id, and has no required ordering with subscriber lifecycle. It is request evidence, never provider-operation completion; only the ordered `thread/status/changed`, `turn/started`, `ContextCompaction`, and terminal controls provide progress and completion evidence.

## Approval and Response Capabilities

- Foreground approvals normalize to compact non-cloneable events with bounded request identity, closed kind, thread/turn/item route, exact-session response capability, and required deny/interrupt facts. Command text, cwd, reason, permission bodies, raw parameters, and pretty payloads are discarded.
- One shared response state belongs to its exact originating session: response-required, automatically denied, or caller-denied. A foreign session or second response is rejected locally. Protocol-specific denial exists for command-execution, file-change, and permission-expansion approvals without deciding product policy.
- The ordered full profile offers compact approvals directly to its sink. Its bounded pre-bind prefix may automatically deny command/file-change but cannot deny permission without exact durable stop ownership; absent that authority retires the session. A failed automatic denial leaves response authority unexercised and retires exact connection authority rather than fabricating a response.
- A routed approval completion is `NotRequired` for command/file-change denial, or `DurableStopOwned(operation, target, attempt_disposition)` for permission denial. Permission admission must return the exact durable operation/target with interrupting-approval cause and whether its sole stop attempt has crossed a request byte; only then may denial be sent, and response state advances only after that write succeeds.
- A full pre-bind prefix returns typed capacity rejection after closing and releasing its retained prefix; an approval rejected before retention receives no denial. Target-local presentation failure may auto-deny command/file-change without invalidating the connection, but permission failure without proven target closure or durable stop ownership leaves response authority unexercised and retires the exact connection. Generic sink failure returns exact approval ownership, attempts no permission denial without that ownership, and retires connection authority.
- After valid permission admission, the driver finishes any interleaved request response, then dispatches the correlated sole stop only when `attempt_disposition` proves no byte crossed; if that attempt already dispatched, it joins the same result and emits no second interruption. Target failure during pre-bind reconciliation fails that binding; top-level polling still reports the typed target-local presentation failure.
