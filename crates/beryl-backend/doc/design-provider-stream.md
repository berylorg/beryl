# Provider Stream

This supplement is normative only for its bounded backend provider-stream role and is governed by
[design.md](design.md). It does not independently declare engineering rigor.

## Incremental Typed Ingress

- Provider-capable foreground ingress incrementally selects the exact pinned message and item schema before retaining a size-unbounded field, emits bounded typed fragments at UTF-8 scalar boundaries, and structurally discards unneeded values. It has no raw capture, generic message limit, whole provider DOM, arbitrary-order tolerance, generic item, or materialized event graph.
- The closed item union preserves every public pinned item variant except deliberate exclusions. Unknown variants, malformed required fields, invalid indices, impossible lifecycle, ambiguous discriminants, or unrepresentable required payloads fail the stream or produce explicit non-complete outcome; they never disappear behind completion. Pinned source/schema evidence governs required method/item discriminant order.
- The pinned Web-search catch-all is the sole lossy variant: it emits closed `Other` while consuming and retaining none of its arbitrary payload. It does not admit a generic unknown item, enum, object, raw JSON, or materialized fallback.
- Raw reasoning content and `item/reasoning/textDelta` bytes are consumed and discarded; only lifecycle, exact identity, index, and provider summary text where supplied may cross the boundary. Standalone `imageGeneration` base64 `result` is consumed and discarded without construction, decoding, spooling, logging, or reconstruction. The standalone `image_gen.imagegen` generated-media item retains exact identity, lifecycle timestamp, status, optional revised prompt, and optional authenticated `savedPath`, but never `result`; missing or empty `savedPath` is typed missing output. Hosted `image_generation` is not a producer contract unless pinned schema/source evidence establishes it.
- Normalized items preserve exact route, source order, lifecycle, status, typed public fields, and provenance without creating transcript, catalog, GUI, or durable-history policy. Native tools, dynamic tools, collaboration tools, external MCP tools, and reasoning remain distinct activity sources; no human-facing label, display policy, or inferred model/reasoning metadata is made.
- Activity output carries stable thread, turn, and item identity; raw protocol item type; raw command text for command-execution when provided; raw tool-name fields when provided; raw item status when provided; lifecycle status; and provider reasoning-summary detail when provided. Command arguments never become display labels or a replacement tool identity.
- A collaboration activity retains bounded receiver thread id, closed target-agent status, and optional spawn model/reasoning metadata only when the collab-agent item supplies them. Missing spawn metadata remains absent and is never inferred from configuration, model-list defaults, parent state, receiver ids, `agentsStates`, nicknames, or caller state; it remains distinct from metadata-only thread-read provider/nickname fields.
- File-change activity retains counts derived only from explicit `fileChange` records and exposes a raw file-change path only when those records name exactly one unique path. Reasoning text-delta output retains exact item identity and `content_index`, never delta text, a text page, owned value, diagnostic copy, or replay copy.
- Completed command-execution, file-change, MCP-tool, dynamic-tool, collaboration-tool, and standalone-image observations reject that kind's `inProgress` status; started observations may retain it. Optional fields remain absent when the provider omits them, and no normalized activity invents missing status, model, reasoning, path, label, or producer fact.
- `SubAgentActivity` is completion-only and remains distinct from ordinary paired start/completion. Structurally valid start evidence is emitted only as a typed lifecycle issue, never discarded as schema error or presented as an ordinary provider frame. A collab-agent spawn completion with accepted spawned-thread id and nickname emits one bounded compact subagent-label update; remaining notification fields discard.
- Item-specific deltas retain only their exact expected item kind and bounded nonnegative protocol indices. A delta kind mismatch is not silently converted into another item. A size-unbounded string, list, object, or binary-excluded field is never an owned `String`, `Vec`, raw JSON, or `serde_json::Value` at this boundary.

## Ordered Controls, Dynamic Tools, and Backpressure

- One provider-capable session offers controls, approvals, dynamic-tool arguments, and provider operations to one caller-supplied ordered sink at their exact read position. It exposes no independent receipt, generic drain, deferred raw FIFO, cloned envelope, or post-allocation schema check. While a fragment exchange waits, it reads no further transport byte; a valid sink progresses independently or returns typed cancellation, timeout, receiver loss, or closure.
- Dynamic-tool normalization retains bounded thread, turn, call, namespace, and tool identity plus one exact-session response capability. After pinned route/discriminant validation it streams argument structure and bounded scalar fragments to the registry sink under backpressure. A valid but unknown/invalid installed tool yields one typed rejection with that authority; envelope-order, duplicate-discriminant, or late-identity failure invalidates the connection.
- Approval controls retain their compact response authority as specified by live control. Unknown notifications discard in source order; unsupported server requests discard then fail the connection; schema-invalid known messages are fatal. Non-provider response retention remains separately fixed-capacity and never becomes a provider fallback.
- `thread/name/updated` is structurally discarded and has no raw-event surface or title authority. Ownerless known notifications, including complete turn-diff updates, are structurally discarded before payload and expose no event.

## Polling and Repair Observation

- Quiet polling is one boundary over the same transport reader: a quiet interval makes no progress, while transport failure, process exit, protocol failure, and schema-invalid known messages are explicit fatal results. Transport loss is never converted to schema failure or normal completion.
- Exact-thread `thread/status/changed`, `turn/started`, typed `ContextCompaction` lifecycle, and matching `turn/completed` controls are the only provider progress/completion evidence. Status is closed `active`, `idle`, or `systemError`, including before a CAS turn id; controls retain exact thread, turn, and item identities and cross the sink in wire order. Successful terminal follows published idle; failure follows `systemError`; interrupted terminal does not prove a prior `systemError` cleared.
- Thread-status and usage controls retain only bounded route identity, closed status facts, a fixed bitset of recognized active-status flags, and fixed-width required counters. Unknown flags and incidental status fields discard; a required counter outside its final numeric domain makes the control explicitly unavailable. `thread/started` retains only bounded compact thread-started metadata sufficient to observe accepted subagent nicknames and distinguish idle, active, system-error, and not-loaded loaded-thread state.
- Exact `0.146.0` `turn/completed` retains terminal identity, status, closed error facts, and at most one shared 4,096-byte diagnostic projection. Its empty `items`/`notLoaded` payload is neither exposed nor synthesized as a full-item snapshot. An interrupted terminal does not prove no same-target later item: that item remains source-ordered and either reaches its target or returns typed target closure and retires the connection.
- Token usage retains only exact app-server-provided values from stream notifications or read-only responses. Rate-limit normalization scans against bounded active-model interest and returns at most one exact bounded bucket with fixed short/weekly window facts or ambiguity/unavailable; it retains no unmatched bucket or collection, and `limitId`/`limitName` remain respectively protocol-identity/display-label bounded values.
- Latest per-thread token usage exposed through read-only metadata normalizes to the same transient exact usage value; the backend never estimates context from transcript text or local tokenization. `fs/readFile` is not a normalized backend API: it neither materializes a base64 file response nor decodes a whole byte vector.
- Provider and control ordering is retained through request response, item lifecycle, terminal facts, dynamic-tool response, and approval response. A source message that exposes a large field before its required route may borrow one connection-scoped unattached observation capability; trailing route validation seals it or releases all pages. The backend neither selects storage nor publishes durable state.
- The private repair adapter reuses this closed incremental item union for its one exact terminal snapshot. It emits final item facts, not synthetic starts, deltas, timestamps, approvals, or source sequence positions.
