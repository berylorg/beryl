# Goals

Provide a reproducible, bounded process and protocol boundary for live Beryl acceptance runs against an explicit frozen executable and isolated Beryl home, with launch-mode-specific workspace state.

Keep acceptance evidence attributable to one run while retaining exact ownership of every Beryl and descendant process created by that run.

## Non-goals

- Defining feature-specific assertions such as lifecycle-yield sequencing, backend lineage, or plan completion.
- Defining another diagnostic wire protocol or changing the user-facing `beryl_diagnostic` dynamic-tool schema.
- Discovering, terminating, or deleting processes or files by broad path, process name, or ambient machine state.

# Decisions

## Ownership Boundary

- `beryl-app` owns the diagnostic-child protocol, process supervisor, narrow acceptance-session facade, deterministic bounds, cleanup, and evidence schema.
- The `beryl` package owns the `beryl-acceptance` command-line entry point and the versioned bounded request-plan input.
- Feature-specific live acceptance owns its request plan and post-run assertions outside this system. A successful harness run proves transport, process, and evidence mechanics only.

## Launch And Protocol

- Every run requires an absolute frozen Beryl executable, an explicit isolated Beryl home, a non-existing evidence destination, a bounded run identity, and nonzero limits within Beryl-owned maxima.
- A fresh-workspace run may use an existing regular frozen executable located inside its execution workspace. That placement does not make the executable or workspace cleanup-owned, and executable evidence continues to identify the exact pre-launch byte stream by byte count and digest.
- The isolated home and evidence destination must remain separate from each other and from the execution workspace, and the executable must remain separate from both the isolated home and evidence destination. Validation rejects equality or ancestor/descendant containment for those cleanup- or publication-sensitive pairs; executable/execution-workspace containment is the sole permitted overlap.
- The typed acceptance launch mode is either `fresh_workspace` or `existing_home_recovery`. Fresh-workspace launch requires an existing absolute host workspace and retains the existing isolated-home behavior. Existing-home recovery requires the isolated home to exist as a directory and forbids a host-workspace input. Invalid mode and path-state combinations fail validation before process launch.
- Live diagnostic acceptance is supported only on host Windows, where the session owns the exact child and descendants through one Windows Job Object. Unsupported hosts fail validation before process launch; this system makes no non-Windows descendant-ownership claim.
- The acceptance session launches the frozen executable through the existing diagnostic supervisor with `--diagnostic-target-stdio`, `--beryl-home-dir`, and an internal hidden acceptance-startup-gate flag. Fresh-workspace launch additionally supplies the existing canonical `--host-path` option. Existing-home recovery omits `--host-path` so Beryl restores the workspace already registered in the isolated home instead of registering a duplicate workspace.
- Launch mode and optional host-workspace state are additive to the internal typed launch object. Ordinary diagnostic-child dynamic-tool startup retains its existing arguments and schema.
- An acceptance-gated target reads and validates one fixed byte-bounded stdin gate frame immediately after CLI parsing and before tracing, workspace resolution, application bootstrap, GPUI, backend, or shell startup. EOF, an invalid frame, or an oversized frame exits before application code can create a descendant.
- The supervisor spawns the gated direct child, configures and assigns its kill-on-close Job Object, then releases the stdin gate. The target emits one fixed bounded pre-protocol ready frame after consuming the gate; the supervisor deadline-bounds that synchronization before sending the normal diagnostic v1 handshake. Job setup or assignment failure leaves the gate closed and performs exact direct-child cleanup.
- The session uses the existing strict diagnostic-child protocol version, framing, handshake, request identities, command vocabulary, and response parsing. Request plans cannot introduce commands or protocol fields outside that authority.
- Before process launch, the request-plan boundary compiles every entry through `beryl-app`'s canonical diagnostic-operation authority. Compilation resolves the effective timeout, validates operation arguments and Beryl-owned maxima, and proves that every protocol request frame the operation can issue fits the diagnostic frame bound. Any unsupported, malformed, or excessive public plan rejects the whole plan without starting a process. Exact encoded-frame boundary coverage belongs to the compiler and protocol layer because the public plan-file and operation-payload maxima are stricter than the frame maximum and cannot currently express an otherwise-valid oversized frame.
- The configured request count bounds logical plan operations. Compilation separately derives the worst-case expanded protocol-request count: one request for a one-shot operation and the exact maximum poll count implied by a normalized wait timeout and poll interval for `wait_for_state`. The whole plan must fit a Beryl-owned expanded-request maximum, and its worst-case operation budgets must fit the configured total runtime.
- Frame qualification uses the largest request id that the dedicated acceptance supervisor can allocate after its handshake and every worst-case expanded request in the plan. Runtime allocation remains contiguous and exclusive to that supervisor, so a qualified plan cannot later exceed the frame bound merely because an earlier wait polled repeatedly.
- `wait_for_state` is a bounded supervisor/session operation rather than a diagnostic-child wire command. It reuses the same canonical argument normalization, predicate evaluation, identity guards, result shape, and polling limits as the diagnostic dynamic-tool boundary while issuing repeated existing `read_ui_state` requests. It does not execute a blocking wait on the child GUI thread.
- An acceptance wait uses one effective deadline equal to the earliest of its normalized wait timeout, compiled per-operation timeout, and remaining total runtime. It checks that deadline before the first poll and every later poll, never issues a zero-budget request, and returns the latest bounded state only when at least one poll occurred.
- Ordinary ungated diagnostic-target startup has no gate or ready frame and retains the existing v1 launch arguments and handshake behavior.

## Bounds And Evidence

- Request plans use an explicit schema version, reject unknown fields, and are bounded by path bytes, file bytes, request count, per-request timeout, total runtime, and captured-output bytes before process launch.
- A compiled plan is static and sequential. In addition to one-shot protocol requests it may contain only the canonical bounded `wait_for_state` operation; it has no branching, variables, feature-specific assertions, automatic retry policy, or general workflow semantics.
- Requests execute sequentially. The harness never starts two GUI conversation turns itself and does not implement a feature workflow engine.
- Each request deadline starts before frame construction and includes writer enqueue, child-stdin write, flush acknowledgement, and response receipt. One owned writer task holds child stdin; a timed-out full-pipe write remains attached to the exact child until bounded cleanup terminates the retained Job, joins the unblocked writer and readers, and only then releases the Job handle. If a join exhausts the cleanup deadline, the exact Job and unfinished transport remain owned for an explicit retry.
- Evidence records the run identity, typed launch mode, mode-valid fixture paths, frozen-executable byte count and digest derived from the same read stream, configured limits, child identity, logical operation command, parameter digest, bounded response or error data, bounded stderr, timings, every finish-owned cleanup attempt, final process residue, and publication outcome. A schema version change accompanies the launch-mode field and optional execution-workspace field so recovery evidence cannot be mistaken for legacy fresh-workspace evidence.
- The existing `read_ui_state` response may add feature-owned, content-free terminal and activity correlation fields without creating a new diagnostic command, request field, or acceptance evidence-envelope version. The acceptance harness treats those fields as part of the already bounded response payload and does not copy them into a second evidence model.
- Multi-agent acceptance may consume the diagnostics-feature-owned exact selected-parent terminal identity/status and bounded selected-thread v2 activity sample to correlate parent completion, immediate child subject ownership, lifecycle kind, row status, and nickname-resolution state. Feature-specific pass/fail assertions remain outside this system, and acceptance must not require labels, prompts, reasoning, tool output, model metadata, or `agentPath` in evidence.
- Schema-v5 operation evidence attributes expanded protocol traffic with an optional exact contiguous identity range containing first request id, last request id, and count. One-shot operations record a count of one; waits cover every actual `read_ui_state` poll without retaining an unbounded identity list. The operation's legacy singular request identity, when present, is the last id in that range.
- Parameter bodies are represented by byte counts and SHA-256 digests rather than copied into evidence. Response, request-error, cleanup-error, and stderr payloads record their original byte count, SHA-256 digest, retained UTF-8 prefix byte count, and explicit truncation state.
- The configured captured-output budget applies to the aggregate UTF-8 bytes retained across response, request-error, cleanup-error, and stderr prefixes in deterministic run order. Metadata, fixed-size digests, and byte counters do not consume that payload budget. Publication-failure text is produced only after persistence fails and uses a separate fixed byte bound in the returned in-memory terminal record.
- Stderr byte counts and digests describe the original raw child bytes. Invalid UTF-8 is converted deterministically for the retained prefix, and the encoded replacement text must still fit the remaining UTF-8 byte budget; lossy conversion cannot expand evidence beyond that budget.
- One Beryl-owned SHA-256 implementation serves executable, parameter, response, error, and stderr evidence hashing. It must be qualified by exact standard known-answer vectors, block-boundary cases, and incremental updates before evidence produced by the harness is accepted.
- Evidence publication uses a same-directory pending file and a non-replacing atomic persist after every finish-owned timed cleanup attempt is complete. An existing destination is never overwritten. A successfully persisted record identifies publication as successful; when publication fails, the returned in-memory terminal record identifies that failure without claiming a file was published.

## Cleanup And Failure

- The session owns the exact diagnostic child handle and its Windows Job Object for the entire run. Descendant cleanup follows that ownership rather than guessed process ids or names.
- Malformed protocol data, protocol EOF, request failure, and observed process exit do not discard ownership. The supervisor records stderr and the actual final method only while explicitly shutting down or reaping the exact child.
- Normal completion closes diagnostic stdin first so the target can follow its existing EOF shutdown path, then escalates through bounded direct-child termination and exact process-tree termination when necessary.
- Cleanup polling sleeps for no longer than the remaining phase budget, including the minimum supported three-millisecond initial attempt.
- Consuming session finish performs the configured initial cleanup attempt. If that attempt remains indeterminate, it may consume the caller-supplied recovery-cleanup budget for at most one explicit bounded retry before terminal evidence publication. Startup failure and terminal finish are mutually exclusive consumers of that recovery budget.
- Each finish-owned cleanup attempt records its ordinal, configured budget, actual phase and termination method, bounded error when any, exact known process identity, and verified-reclaimed or indeterminate residue. Cleanup failure, publication failure, and their combination remain separate terminal facts.
- Session finish consumes the diagnostic supervisor so an error cannot trigger another timed cleanup through either session or supervisor destruction. If the pre-publication recovery attempt remains indeterminate, the terminal outcome retains the exact child, Job, and transport owner. After publication that owner permits only explicit non-waiting fail-safe release; it cannot perform another timed retry that would make the terminal record stale.
- Acceptance startup uses its configured cleanup budget exactly once. If that attempt cannot terminate, reap, and join the acquired transport, the startup failure retains the exact Child and every resource acquired at the failing stage: any created Job, any raw child pipes not yet installed, and any installed writer or reader. It returns that stage-accurate state in a must-use owner-bearing result instead of reducing the failure to text or invoking ordinary supervisor defaults.
- The public startup failure exposes a stable typed cause category and bounded message so callers can distinguish validation, executable identity, process launch, Job setup, transport setup, and startup protocol failures without depending on private supervisor errors or parsing text.
- The retained startup owner exposes its process identity and accepts only an explicit caller-supplied bounded cleanup retry. The `beryl-acceptance` caller configures that recovery budget separately from the initial attempt, so additional cleanup time is visible rather than silently charged beyond the failed bound.
- Dropping an unconsumed retained startup owner performs fail-safe handle closure, including the kill-on-close Job, but never starts another timed retry. Callers use the explicit cleanup operation when they require a verified reap and joined transport.
- Dropping an unfinished session performs the configured bounded cleanup attempt once, performs only non-waiting fail-safe release if that attempt remains indeterminate, and does not publish incomplete success evidence. It must not fall through to ordinary supervisor timeout defaults.
- Startup incompatibility, protocol failure, request timeout, malformed or oversized output, interruption, cleanup failure, and evidence-publication failure remain distinguishable bounded outcomes.
