# Reason For Investigation

The original architecture gate for `yield(phase_continue_new_thread)` required proving that a Beryl dynamic tool registered on an orchestration root survives backend `thread/fork`, full `thread/rollback`, unload/resume, and a later child turn. After protocol compatibility and exact managed launch were separated into their own phases, the live retention proof required an exact 0.146.0 lifecycle path that could unload the child and reclaim persistent probe threads. Beryl cannot re-register a missing tool after the fork without losing required backend lineage.

# Outcome

The exact installed target was `codex-cli 0.146.0`. Schema inspection does not establish whether a fork inherits dynamic tools, so a live child `item/tool/call` remains necessary.

The 0.146 experimental schema accepts `dynamicTools` only on `thread/start`. It defines a tagged union: function specs require `type = "function"`, and namespace specs require `type = "namespace"` plus nested tagged function tools. `thread/fork`, `thread/rollback`, `thread/read`, `thread/resume`, and `turn/start` expose no dynamic-tool registration field, and no separate registration request was found.

Beryl's logical `DynamicToolSpec` remains an individual function with optional namespace membership. Its private `thread/start` wire boundary now normalizes unnamespaced functions into tagged top-level function entries and groups namespaced functions into tagged namespace entries with nested tagged functions. Focused backend protocol integration tests cover the exact 0.146 shape, stable grouping order, function metadata, and empty-registry omission.

A Rust live probe exists at `crates/beryl-backend/tests/live_dynamic_tool_fork.rs`. Beryl's production managed-launch boundary accepts a validated absolute Unicode Host Windows executable while preserving ordinary PATH-based launch.

The revised probe's first live invocation validated the exact executable through bounded `--version`, launched it through that managed boundary, and then stopped before root-thread creation. Initialize returned a composed Beryl client user agent shaped as `beryl/0.146.0 ... (beryl; 0.1.0)`, not the CLI banner `codex-cli 0.146.0`. Operator confirmed that CAS reports its version by combining the client project's name with the CAS version. The corrected probe requires the `beryl/0.146.0` prefix while retaining separate exact executable and CLI-banner checks. No model turn ran, no persistent probe thread was created, and managed process/auth cleanup completed.

The probe's original unsubscribe-based unload assumption is invalid on 0.146.0. `thread/unsubscribe` removes the caller's subscription, but the last-unsubscribed thread remains loaded until it has no subscribers and no activity for 30 minutes. A 15-second wait for `thread/closed` or `notLoaded` therefore cannot prove unload.

The exact target exposes explicit lifecycle operations instead. `thread/archive` moves persistent rollout state into archived storage and emits `thread/archived`; `thread/unarchive` restores it, returns the restored thread, and emits `thread/unarchived`; `thread/delete` physically removes active or archived persistent state and emits `thread/deleted`. Beryl now exposes those typed backend primitives, and the live probe uses archive, unarchive, and resume for the rolled-back child before deleting the child and root so task-owned persistent evidence does not remain.

The corrected live probe passed against exact `codex-cli 0.146.0` on August 4, 2026. After the managed-server ownership correction, the final run requalified the same result through launch-first guarded compatibility probing, so connection, initialize, or compatibility failure would leave the server handle available for explicit cleanup. Version-process duration, stdout collection, output size, termination, and reaping are independently deadline-bounded. The run required the registered namespaced lifecycle probe tool in the root turn, bound the full root snapshot to its exact persistent non-fork identity and required model-provider identity, forked that populated root, rolled back every inherited user turn, verified an empty child with direct root `forkedFromId`, unchanged root history, and matching required provider, archived the child, observed its exact archive notification, unarchived it as `notLoaded`, resumed it as idle, and verified empty history plus required and optional runtime semantics again. A later child turn invoked the same registered namespaced tool exactly once and completed successfully. This proves the targeted CAS contract retains Beryl's registered dynamic tools through the full lifecycle path required for repeated `yield` calls from phase children.

The final passing harness rediscovered task-owned active threads through bounded exact-CWD inventory, enriched omitted list lineage through typed metadata-only reads, physically deleted the child before the root, verified final active inventory was empty, and then shut down its client and managed app-server. Independent post-run checks found no process using the exact target executable, no managed token file, and no Cargo or nextest process. No task-owned persistent probe thread, app-server process, listener, or current managed-auth file remained. The existing Beryl process was untouched.
