# Goals

Support bounded operator debugging, live testing, and resource investigation through Beryl-owned diagnostic tools and isolated diagnostic child processes.

## Non-goals

- Exposing arbitrary process launching through diagnostic child control.
- Mutating backend conversation history, semantic graph state, workspace persistence, settings, transcript content, or durable image assets through observation tools.
- Loading additional transcript history, decoding media, or creating renderer resources solely to answer diagnostics.

# Decisions

## Supervisor Diagnostics

- Beryl may expose Beryl-owned app-server dynamic tools on Beryl-created conversation threads for operator-approved debugging, live testing, and resource investigation.
- Supervisor self-observation tools may report bounded snapshots of Beryl process identity, platform memory counters, active workspace/thread identity, managed backend child process ids, retained GUI projections, visible transcript media, and recent media lifecycle events.
- Diagnostic output must be bounded by deterministic item and byte caps. Large strings, paths, labels, error text, media keys, event details, and lists are truncated or omitted rather than returned without limit.
- Diagnostics must not retain image bytes, decoded pixel buffers, GPUI image handles, process handles, backend responses, or transcript payloads solely to make later diagnostics more detailed.
- Recent diagnostic event logs are metadata-only bounded rings.
- Supervisor activity-lifecycle diagnostics retain at most 256 recent metadata-only events and at most 128 KiB of aggregate retained identity text. Each exact thread, turn, or item identity field is limited to 512 UTF-8 bytes; missing, blank, or over-bound identities are represented by explicit validity metadata rather than substituted labels or inferred keys.
- Activity-lifecycle events record a monotonic sequence and elapsed time, the capture stage, normalized lifecycle or stream-failure kind, bounded exact thread/turn/item identity when valid, raw protocol item type and status when available, projection match outcome, row status before and after application, and the count of rows affected by a turn or thread fallback.
- Activity-lifecycle diagnostics omit commands, working directories, paths, tool arguments, tool output, display values, labels, prompts, agent messages, reasoning text, model metadata, and backend response bodies. Capture must not change Activity projection lifecycle, sorting, retention, or rendering behavior.
- The activity-lifecycle ring is in-memory session state owned with the Activity projection. It is cleared with workspace/backend-session Activity teardown and is not persisted as conversation history or workspace state. When the separate operator-enabled Activity diagnostic file capture is active, an explicit content-free durable DTO may copy each normalized lifecycle diagnostic event without making the ring itself durable.
- `read_activity_lifecycle_diagnostics` is a read-only supervisor self-observation tool. It accepts optional bounded `afterSequence` and `limit` arguments and returns a deterministic oldest-to-newest slice plus capacity, retained count and bytes, oldest and newest sequence, omission counters, and truncation state. Reading the ring must not query or activate the backend, load transcript history, or mutate visible GUI state.
- Supervisor Activity presentation diagnostics retain at most 256 recent metadata-only events, at most 512 KiB of aggregate encoded event data, and at most 64 KiB for one event. A rendered-window sample contains at most 32 rows. Each exact thread, turn, or item identity field is limited to 512 UTF-8 bytes and uses the same explicit missing, blank, or over-bound validity representation as Activity lifecycle diagnostics.
- Activity presentation events use their own monotonic sequence and elapsed time. A `projection_changed` event records the post-prune Activity projection revision, the newest lifecycle sequence incorporated by that revision, total row count, and running, finished-ok, and finished-error counts. The revision advances only when the derived ordered row model, including row status, changes.
- A `shell_notified` event records the newest Activity projection revision for which the Shell requested model refresh. Repeated notifications that acknowledge no newer Activity revision are not retained as new presentation events.
- A `render_sample` event records a monotonic Activity render revision, the current projection revision, the newest projection revision acknowledged by Shell notification, panel visibility, bounded selected-thread identity, selected-thread row count, rendered range, configured overscan count, and a deterministic ordered sample of the rendered rows. Consecutive renders with identical diagnostic state are coalesced.
- Each sampled row records its rendered index; bounded exact thread, turn, and item identity; row status; selected status-indicator theme role; whether the resolved color came from that role or its renderer fallback; and resolved eight-bit RGBA value. Row samples follow rendered order and expose explicit item, identity-byte, event-byte, and ring-eviction truncation or omission counters rather than substituting labels or unbounded payload.
- Presentation events describe Activity model refresh, Shell invalidation, and GPUI element-tree construction inputs. A render sample proves which status, role, and resolved color Beryl supplied while constructing that row; it does not claim that a GPU pixel was painted. A visual capture or lower renderer evidence is required to classify a discrepancy after correct render input as GPUI reconciliation or paint behavior.
- Activity presentation diagnostics omit commands, working directories, paths, tool arguments, tool output, display values, agent labels and paths, prompts, messages, reasoning text, model metadata, theme documents and names, backend response bodies, and pixel or image data. Capture must not alter Activity identity, lifecycle, sorting, retention, viewport bounds, theme resolution, notification, or rendering behavior.
- The Activity presentation ring is in-memory session state owned by the Shell presentation boundary. It is cleared with workspace/backend-session Activity teardown and is not persisted as conversation history or workspace state. When the separate operator-enabled Activity diagnostic file capture is active, an explicit content-free durable DTO may copy each normalized presentation diagnostic event without making the ring itself durable.
- `read_activity_presentation_diagnostics` is a read-only supervisor self-observation tool. It accepts optional `afterSequence` and `limit` arguments, with `limit` defaulting to and capped at 64, and returns a deterministic oldest-to-newest slice plus event and row capacities, retained event count and bytes, oldest and newest sequence, omission and eviction counters, and truncation state. Reading the ring must not force a render or paint, reveal hidden content, activate the Activity panel, query or activate the backend, load transcript history, or mutate visible GUI state.

## Activity Diagnostic File Capture

- Activity diagnostic file capture is an explicitly enabled app-wide Beryl diagnostic preference and defaults to disabled. Persisting the preference records operator intent; it does not make Activity capture permanently active or make Activity projection state durable.
- Beryl constructs the capture directory and filenames from the configured Beryl home. V1 data records use only `diagnostics/activity-capture/activity.jsonl` and `diagnostics/activity-capture/activity.previous.jsonl`. Exclusive ownership uses the fixed `diagnostics/activity-capture/activity.lock` target, which contains no diagnostic records. No GUI, dynamic tool, workspace value, backend value, or event payload may supply any capture or lock path.
- Each data file is capped at exactly 10 MiB, including segment headers, JSON records, and newline delimiters. The combined data-file capacity is exactly 20 MiB. Lock files, directory metadata, and filesystem allocation granularity are outside the JSONL data-byte capacity and must not contain diagnostic records.
- Rotation admits only whole newline-terminated records. Before a record would make the current segment exceed 10 MiB, the writer removes the old previous segment, renames the current segment to previous, and creates a new current segment with a bounded header before admitting the record. A failure at any rotation step stops that capture generation rather than exceeding either segment cap.
- A record that cannot fit in an otherwise empty segment after its required header is omitted and increments a bounded oversized-record counter. Capture never splits one JSON record across segments.
- One process may own capture files for a Beryl home at a time. Capture activation acquires an exclusive Beryl-owned file lock before recovery or writing. Another process using the same home reports capture unavailable and must not rotate, repair, truncate, or append to the files.
- Activation validates both fixed segments before append. An unterminated tail in either segment is truncated to its last complete newline. After tail repair, a present segment is structurally usable only when it begins with a complete supported `segment_header` and every remaining non-empty line is one complete supported record shape; otherwise it follows the unusable-segment rule below. A missing previous segment is accepted as absence of older evidence. When both segments are missing, including on a fresh home, Beryl creates only a current segment with a bounded recovery header. A missing current segment with a valid previous segment creates a new current recovery header without changing the previous segment. An oversized or structurally unusable previous segment is deleted; an oversized or structurally unusable current segment is replaced with a new bounded recovery header. These rules also resolve every observable partial-rotation state: current-only continues as current-only, previous-only gains a new current segment, and two valid segments continue unchanged. Capture fails closed if these bounded repairs cannot restore every present data file within its cap and a valid current segment.
- Capture preserves complete prior records across ordinary restart and enablement. It appends a new bounded session or segment header rather than clearing valid files. A crash may tear or lose the final buffered record; recovery makes no claim that the last pre-crash record reached durable storage.
- Durable JSONL schema v1 serializes only the record shapes and fields enumerated here. Every record has integer `schemaVersion` equal to `1` and a `recordKind` enum. No internal diagnostic struct is serialized wholesale, and a future field is excluded until a later schema version explicitly admits it.
- A v1 `segment_header` record contains only `schemaVersion`, `recordKind`, optional bounded `buildIdentity`, `processId`, bounded random `sessionId`, `captureGeneration`, `segmentSequence`, and `startedUnixMillis`.
- Each v1 event record contains only `schemaVersion`, `recordKind`, `captureGeneration`, `captureSequence`, `sourceSequence`, `elapsedMicros`, and the fields for its exact kind below. Capture sequence is assigned before nonblocking enqueue so an admitted `capture_gap` can describe missing capture-sequence ranges.
- A v1 diagnostic identity contains only `validity`, optional `value`, and `originalByteCount`. `validity` is one of `valid`, `missing`, `blank`, or `over_bound`; `value` is present only for `valid` and retains the ring's bounded exact identity.
- A v1 bounded protocol string contains only optional bounded `value`, `originalByteCount`, and `truncated`.
- A v1 `lifecycle_event` adds only `stage`, `category`, `kind`, `threadIdentity`, `turnIdentity`, `itemIdentity`, `itemType`, `itemStatus`, `projectionOutcome`, optional `beforeRowStatus`, optional `afterRowStatus`, and `affectedRowCount`. Identity and protocol-string fields use the v1 shapes above rather than internal ring structs.
- A v1 `projection_changed` record adds only `projectionRevision`, optional `newestLifecycleSequence`, `totalRowCount`, `runningRowCount`, `finishedOkRowCount`, and `finishedErrorRowCount`.
- A v1 `shell_notified` record adds only `projectionRevision`.
- A v1 `render_sample` record adds only `renderRevision`, `projectionRevision`, `newestNotifiedProjectionRevision`, `panelVisible`, optional `selectedThreadIdentity`, `selectedThreadRowCount`, `renderedRangeStart`, `renderedRangeEnd`, `overscanRowCount`, `sampledRows`, `rowSampleTruncated`, `eventBytes`, and `eventBytesTruncated`. Before any Shell notification, `newestNotifiedProjectionRevision` is the canonical initial projection revision `0`. Each `sampledRows` entry contains only `renderedIndex`, `threadIdentity`, `turnIdentity`, `itemIdentity`, `rowStatus`, `statusIndicatorThemeRole`, `colorSource`, and four-byte `resolvedRgba`.
- A v1 `capture_gap` record contains only `schemaVersion`, `recordKind`, `captureGeneration`, `captureSequence`, `firstDroppedCaptureSequence`, `lastDroppedCaptureSequence`, `queueFullDropCount`, and `queueDisconnectedDropCount`. It contains no source event payload.
- V1 integer sequences, generations, times, revisions, counts, byte counts, ranges, and row indexes are non-negative 64-bit values in JSON; `processId` and `schemaVersion` are non-negative 32-bit values; flags are booleans; each RGBA channel is an unsigned byte. Conversion overflow rejects that input before enqueue and increments a bounded schema-rejection drop counter rather than narrowing or wrapping.
- V1 controlled strings are closed enums serialized in `snake_case`. Lifecycle stage/category pairs are `activity_ingress`/`lifecycle`, `fallback`/`fallback`, or `stream_failure`/`stream_failure`. Their allowed kinds are respectively `started`, `updated`, `completed`; `turn_completed`, `thread_closed`, `thread_archived`, `thread_deleted`, `protocol_error`; or `local_turn_failure`. Projection outcomes are `inserted_running`, `matched_running`, `reactivated_existing`, `matched_existing`, `inserted_completed`, `no_running_match`, or `finished_running_rows`. Row statuses are `running`, `finished_ok`, or `finished_error`. Indicator roles are `activity.indicator.running`, `activity.indicator.ok`, or `activity.indicator.error`; color sources are `theme_role` or `renderer_fallback`. An unknown controlled value is rejected before enqueue, is not persisted under schema v1, and increments the bounded schema-rejection drop counter. A failure while serializing an already-admitted v1 DTO remains a writer failure and fails the generation closed.
- File capture applies every content prohibition of both Activity diagnostic rings. It omits commands, working directories, paths, tool arguments, tool output, display values, labels and agent paths, prompts, messages, reasoning text, model metadata, theme names and documents, backend response bodies, pixel or image data, and unbounded error text. Future fields are excluded until design authority and the durable DTO allowlist explicitly admit them.
- Activity producers never perform capture filesystem work or blocking queue sends. They use a bounded nonblocking handoff to one writer owned for the Shell application lifetime. A full or disconnected queue drops the capture copy, increments bounded counters, and does not delay or alter projection, notification, theme resolution, rendering, diagnostic-ring retention, or backend work.
- The writer alone serializes, repairs, rotates, and appends. When records were dropped, it may emit one bounded `capture_gap` record with aggregate counts before the next ordinary record; failure to emit the gap record does not retry unboundedly.
- Each enable attempt creates a new capture generation. Disabling gates producers immediately. Queued records carry their generation and cannot be written by a later enable generation. Disable and process shutdown signal the writer best-effort without synchronously flushing or joining it on the GPUI thread.
- Filesystem, serialization, lock, repair, rotation, or writer failures fail that capture generation closed. The configured preference may remain enabled so restart or an explicit disable/re-enable can retry, but runtime status must distinguish configured intent from active capture.
- Bounded runtime status reports configured state, active, starting, stopping, unavailable, or failed state; capture generation; written and dropped record counts; oversized count; repair and rotation counts; and a bounded error category. Status never exposes the configured Beryl home, capture path, event content, or raw filesystem error text.
- Workspace switching, Activity teardown, backend-session replacement, pending new-thread selection, and Activity-panel visibility do not own or reset the app-lifetime file controller. Existing in-memory rings retain their current independent teardown semantics.
- Process and memory diagnostics may expose platform counters. Windows builds should expose GUI process id, known child backend process ids, Private Bytes, Working Set, commit-related counters when available, handle count, and thread count. Unsupported counters are reported unavailable rather than guessed.
- Visible-media diagnostics report only currently retained or visible GUI projection state. They must not load history pages, read files, decode images, or create GPUI assets just to answer.
- Diagnostic child `read_ui_state` reports the latest retained selected-parent turn as exact thread id, turn id, and terminal status only when the latest retained turn is completed, interrupted, or failed and both identities fit the diagnostic identity-field bound. It does not substitute an older terminal turn while a newer selected turn is queued, starting, or running.
- Diagnostic child `read_ui_state` may report a bounded selected-thread sample of retained multi-agent v2 lifecycle activity. Each sample record contains only the exact parent event thread, turn, and item ids; optional exact child subject thread id; normalized lifecycle kind; and row status.
- Multi-agent v2 diagnostic activity excludes legacy collaboration records, labels, display values, prompts, reasoning, tool output, model metadata, reasoning-effort metadata, backend-generated nicknames, and `agentPath`.
- The multi-agent v2 activity sample is a deterministic newest-prefix projection of records visible for the selected thread. It retains immediate parent event identity for nested activity rather than rewriting records to a root identity, and it never retains state solely for diagnostics.
- The sample is capped at 64 records, 64 KiB of aggregate identity text, and 512 UTF-8 bytes per exact identity field. A record with a missing required identity or an over-bound identity is omitted; item-cap, byte-cap, and invalid-identity omission set an explicit truncation flag. No selected thread produces an empty, non-truncated sample.

## Diagnostic Child Process

- Beryl may expose a dot-free diagnostic child-control dynamic-tool namespace implemented by the supervisor Beryl.
- The supervisor controls at most one diagnostic child process at a time.
- A diagnostic child runs with an explicit Beryl home directory distinct from the supervisor home. Launching a child against the supervisor home is rejected.
- Diagnostic child startup uses the supervisor's current executable by default, or a caller-supplied explicit compatible Beryl executable when the operator needs another build.
- An explicit executable path is diagnostic child identity. It is spawned directly without shell interpretation and must not turn child control into arbitrary command-line or environment mutation.
- Startup reporting includes the actual executable path when available.
- Starting a custom executable must prove the child supports Beryl's diagnostic-target stdio mode before reporting it as started.
- Unsupported, incompatible, missing, or non-executable targets fail with bounded diagnostic errors and must not leave unmanaged child lifecycle.
- If cleanup after failed startup cannot complete immediately, the supervisor retains ownership for status and later stop retry.
- Supervisor-to-child control uses a Beryl-owned bounded local control protocol over child stdio. Child stdout is reserved for protocol frames; logs use stderr or files.

## Diagnostic Child Controls

- Diagnostic child controls are supervisor dynamic tools for testing an isolated child Beryl instance. They are not visible end-user controls in the ordinary workspace screen.
- Child control may switch workspaces or threads, list workspace threads from bounded child-owned inventory state, select a pending new-thread draft, submit bounded text through the child composer, request soft or hard stop for the child's exact selected active turn, scroll transcript, close transient popups, and wait for bounded UI or turn-state predicates.
- Child commands must drive the same internal application command paths and state transitions as corresponding visible UI interactions or retained UI projections.
- Child commands reject ambiguous, stale, missing, or unavailable targets and report timeout or partial state instead of blocking indefinitely.
- A child command must not fall back to another workspace, thread, runtime target, turn, stop target, or input path when the requested target cannot be used exactly.
- Child composer submission may synthesize user-authored transcript input only for the isolated child and only through ordinary validation, draft acceptance, transcript insertion, new-thread creation, active-turn steering, compaction queueing, and rejection behavior.
- Child soft stop uses the same exact selected-thread active-turn interruption behavior as the visible status-line `Soft stop` action.
- Child hard stop uses the same exact selected-turn interruption and backend-exposed hard-stop targets as the visible popup, but the diagnostic request supplies deliberate activation instead of the visible three-second hold affordance.
- Stop commands may interrupt only the child's exact selected active backend turn or selected active compaction operation when Beryl knows the interruptible backend turn id.
- Hard stop must use only exact backend-exposed termination handles and never guessed OS pids, process names, working directories, or local process trees.
- Child wait commands observe bounded UI state without creating loading UI solely for diagnostics and return latest bounded state on timeout.
- Diagnostic child UI-state and command results report backend-unavailable workspace state and backend-unavailable submission/thread-listing rejection distinctly from ready, opening, workspace-idle, and blocked shell states.

## Boundaries

- Diagnostic child GUI-control commands must not edit backend history, apply settings, mutate semantic graph data, mutate the supervisor instance, bypass availability checks, or use direct app-server calls when a child-owned UI/application path defines the behavior.
- Diagnostic child control is independent of the child app-server turn lifecycle. Supervisor commands reach the child over the child control channel rather than through that child's dynamic-tool stream.
- Beryl-owned dynamic-tool results use the existing app-server dynamic tool-call response contract for the supervisor-facing call. The child-control protocol remains an internal Beryl process boundary.
