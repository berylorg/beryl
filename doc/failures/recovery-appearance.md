# Recovered Editor Appearance

The first fresh appearance implementation assumed ordinary live/fencing appearance eligibility
also covered an adopted recovery resident. Independent phase 775 review found that adoption keeps
the resident recovery-fenced. Allowing that state alone was insufficient: native selected-shell
tests in run `1f9d18d5-a4bb-4e11-b61e-7228a836e00b` failed with widget `Busy` during appearance commit.

Widget successor adoption invalidates predecessor protection but retains the exact protection cut.
Appearance changes reject any retained protection. The app had discarded the predecessor snapshot
without releasing that cut. Correct adoption consumes the exact protection immediately after the
checked successor transfer, using the existing widget release API. It keeps the widget disabled and
the resident recovery-fenced. Appearance eligibility then accepts only adopted recovery custody
with a fresh service/close ticket and no predecessor snapshot.

Selected and threadless native fixtures must both qualify appearance replacement. Threadless-only
evidence cannot prove editor eligibility or protected-widget behavior. Failed fixture runs did not
reach their normal home cleanup; their random temporary paths were not reported and must not be
guessed or swept. Final candidate publication and cancelled-request settlement remain separate.
