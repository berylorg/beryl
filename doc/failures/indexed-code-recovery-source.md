# Indexed Code Recovery Source Qualification

The first-conversation recovery fixture mounts a newly committed empty conversation. Editing
its fresh composer is not a way to seed a transcript Code record. The transcript renders
conversation records; the unsubmitted draft remains editor state. The indexed provider's
composer source representation refers to recorded content, not the current editor draft.

An attempted replacement-loading test inserted a 2,000-line fenced draft and waited for a Code
range. Runs `60f9f040-4aa7-40bb-9b1b-3e1bbdd1755e` and
`1bc879ed-70ea-4c18-9d97-39f2ad0d123b` timed out after 21.5 seconds. The latter captured
zero transcript records, metadata entries and mounted Code panels, with no resource demand.
Recovery itself had completed and its identity, claim and subscription assertions had passed.

The corrected regression waits for the actual editor mutation to settle at the inserted source
extent, then verifies that the empty transcript acquires neither Code nor resource demand across
subsequent frames. This is draft isolation evidence, not replacement Code loading qualification.
Replacement-loading coverage must introduce actual conversation records through an admitted
history/capture workflow and then exercise indexed delivery on the replacement panel. Do not
change the empty first-conversation mount or insert supplied responses to satisfy that gap.

# Virtual Service Reader Attachment

The first-conversation service fixture starts an unmounted running owner. Its virtual shell cannot
resolve that owner through the native mounted-owner lookup. Merely admitting stored CAS history
after recovery therefore does not establish ordinary history polling. Run
`8813ee3b-66bf-4baa-b96f-fcca385d86af` passed the existing seven recovery cases, but the new
stored-Code case timed out after 21.488 seconds waiting for its first indexed range.

Use the existing `test_running_thread_reader` hook with the actual current published reader and
retain that reader through disposal. This is fixture composition, not supplied transcript or
resource delivery. Preserve exact onboarding/draft assertions before admitting history, and keep
virtual provider evidence distinct from native first-conversation qualification.

Admitting history through a local draft submission also consumes the draft held by the recovered
editor. Code loading, input and ten stable frames passed, but a subsequent flush of that old
editor was refused. Run `2898a471-7b96-40b5-b6eb-9b6d8b67949e` exposes the exact close result:
`Resident(Unsatisfied(Recoverable))`. Explicit extra read suspension did not resolve it; the
shutdown draft already suspends those reads.

Flushing and gating the editor before that external submission also fails at final disposal:
run `64bbc1fa-db38-4ee6-89b5-7cc9a4ff4f2d` reported a recoverable disposal refusal after passing
Code loading and interaction. A prior flush does not authorize bypassing successor-editor adoption.

Use the actual mounted submission flow with the existing storage-only execution wake, require
its successor editor under the same claim, and then admit capture events for that submitted turn.
No supplied submission outcome or indexed response is needed. This composes the editor and
transcript ownership normally and preserves the existing disposal/reopen proof. Keep this virtual
provider qualification distinct from native first-conversation startup and real CAS execution.
# Pending Creation Projection Identity

Run `22640f63-7e2d-418d-bbba-d7a16adedc64` passed eleven setup cases but failed the mounted
pending-creation retention case: composer identity and remembered target remained equal while
an ordinary transcript refresh replaced the snapshot allocation. The fixture had equated the
snapshot Arc address with mounted transcript identity. This does not qualify replacement, because
same-view provider refresh can publish a new projection without changing the selected panel.

The visible-identity hook now returns the mounted transcript entity identity alongside composer
mount identity and remembered target. Existing exact claim, editor session, original operation/
lease, exclusion, duplicate-confirmation and close-refusal assertions remain. Snapshot allocation
identity is not a suitable retention assertion once ordinary provider refresh is active.

# Native Threadless Editor Configuration

The native ordinary-command harness used a configurator that always returned
`no editor in this fixture` when it began without a selected conversation. That was sufficient
for threadless recovery, but not for mounting the first conversation after its exact commit.
Run `4aa8054d-3628-437e-a320-3ae6aeded35a` passed 58 selected cases; the new native first-conversation
case reached recovery and was refused by that configurator after 5.758 seconds.

Threadless native startup now supplies the existing empty-editor configurator while retaining its
threadless acquisition and window-service inputs. Initial startup still has no composer. Only an
actual acquired conversation invokes the configurator. Keep the original threadless recovery
regression in the combined qualification; no production recovery fallback is needed.
