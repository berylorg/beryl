# Diagnostic Shell Liveness

## Active child turn stopped diagnostic-shell polling

Phase 11 repeated-root-sibling acceptance used one bounded diagnostic driver against exact CAS 0.146.0. The ordinary root composer turn created a clean first child and started its fixed continuation turn. The last successful shell snapshot showed that exact child turn active with turn streaming pending, two backend receivers, no activation pending, and one 35-character continuation transcript row.

The invalid assumption was that existing short background polling kept every shell-owned bridge responsive throughout this real child turn. Sixteen consecutive two-second diagnostic requests timed out and filled the diagnostic target's capacity-16 queue; later requests then failed immediately as `shell_busy`. The phase marker was written about 24 seconds after the last readable shell snapshot, proving backend/model work continued after the GPUI shell stopped claiming diagnostic requests. This violates the diagnostic-child contract that control requests remain independent of the child app-server stream.

The trace does not show whether the child later invoked `yield`, whether Beryl acknowledged a dynamic-tool call, whether the source turn became terminal, or whether a second backend child exists. It therefore does not invalidate the exact CAS dynamic-tool-retention proof and does not authorize guessing or deleting a possible child identity.

The course correction was to pause repeated-yield acceptance and add bounded evidence correlating sanitized child tool and turn event categories with GPUI poll progress and entry/exit timing for diagnostic-target requests, shell dynamic-tool requests, and turn updates. The metadata-only trace uses a 64-entry overwrite ring plus an atomic heartbeat that the diagnostic stdio thread can read without GPUI participation.

The one authorized instrumented reproduction did not reproduce the stall. The shell remained responsive and its timer, window update, view update, poll entry, and poll exit heartbeats remained current and successful while the ordinary root turn created child 1 and child 1 created child 2. The run ended at its request bound while child 2 remained active, so it was not final lifecycle acceptance and did not establish backend lineage or `plan_complete`. It also did not establish the cause of the earlier stall.

Source inspection nevertheless proved an architectural liveness hole independent of that inconclusive causation: a transient window callback failure could leave the single-flight boolean latch armed forever because callback errors were discarded and only a successful nested view update cleared the latch. The correction replaces boolean latches with exact-generation outcome state. Typed transient GPUI borrow conflicts retry the same generation at the existing cadence; definitive window or weak-view loss releases that generation visibly; successful delivery releases only its own generation before polling; and stale callbacks cannot clear newer work. Deterministic reducer and shell integration tests cover success, retry, definitive release, stale completion, pending rearm, no-pending disarm, and duplicate-arm rejection without changing lifecycle semantics.
