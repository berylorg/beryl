# Diagnostic Acceptance Launch

## Fresh workspace could not be opened through the existing dynamic-tool launcher

The first Phase 12 acceptance attempt prepared a fresh isolated Beryl home, execution workspace, frozen corrected executable, and evidence template. The available `beryl_diagnostic.start` contract accepted only the child home and optional executable path. It could not pass the execution workspace through Beryl's existing `--host-path` startup option, and the child-control API could only switch to a workspace already registered in that empty home.

Reusing or cloning a prior live fixture would have weakened run identity and persistence evidence. Hand-authoring Beryl's REDB workspace state was not safe. Recreating the earlier stateful PowerShell stdio driver was also invalid because the repository's Rust-first automation authority requires Rust to own long-running multi-process state, schemas, timeouts, cleanup, and evidence publication.

Operator approved a separately planned correction. The diagnostic supervisor now accepts an optional typed host workspace for acceptance launches while ordinary dynamic-tool startup remains unchanged. A narrow `beryl-app` session facade owns the existing protocol, exact child process tree, bounds, cleanup, and evidence; the `beryl-acceptance` executable owns typed CLI input and a bounded versioned request plan. Feature-specific lifecycle assertions remain in the later live-acceptance phase.

The first transport correction then exposed a startup-failure ownership limit. Gated acceptance launch can retain the exact Child, Job, pipes, and writer inside its local supervisor when bounded cleanup fails, but `AcceptanceSession::start` reduces that failure to a string and drops the supervisor. Its ordinary destructor retries with larger default timeouts. A three-millisecond configured cleanup minimum cannot guarantee termination, reap, and thread joins, so neither silently exceeding that budget nor dropping the owner is valid. The remaining architectural correction must return an owner-bearing startup-failure result for caller-visible explicit cleanup, or Operator must approve a different cleanup contract.

The approved correction makes acceptance startup return a must-use structured failure. Its opaque owner retains the exact staged child, any created Job, and every installed transport resource after the single configured cleanup attempt. Callers inspect the bounded original cause and exact retained identity, retry cleanup only with an explicit nonzero bounded duration, and keep ownership after an indeterminate retry. Dropping an unconsumed owner performs only non-waiting writer closure, direct termination request, and kill-on-close Job release; it does not start a timed retry or join. The acceptance CLI owns a separate bounded recovery-cleanup option and invokes it explicitly before returning startup failure.

Completion review invalidated two subtler variants of that correction. Reading a complete gate line and checking its size afterward was not bounded; the target now caps consumption and buffering at the fixed maximum plus one detection byte before it can enter bootstrap. Closing the kill-on-close Job before bounded transport joins also weakened a retained retry owner when a join exhausted its deadline. Cleanup now terminates the retained Job to reclaim descendants and inherited pipe handles, keeps the exact Job handle while joining the owned writer and readers, and releases it only after every join succeeds. Writer-thread spawn failure likewise returns the original stdin pipe to the staged process owner instead of dropping it with the failed spawn closure.

An acceptance request no longer invokes the ordinary supervisor's implicit observed-exit reaper. It retains the exact exited child and transport until the session's explicit bounded finish, preserving both ownership and the actual `observed_exit` method. The public startup failure exposes a stable cause category rather than requiring callers to parse flattened supervisor text. Exact Windows cleanup tests retain known-live process handles through the transition; PID reopenability and `tasklist` output are not valid terminal-process evidence.

Phase 13 source review found the same hidden-retry hazard at successful-session finish. `AcceptanceSession::finish` returned immediately when its configured cleanup failed, after which `AcceptanceSession::drop` repeated that cleanup and `DiagnosticChildSupervisor::drop` could retry again with ordinary larger defaults. None of those destructor attempts appeared in returned or persisted evidence. Publishing before a later owner-bearing timed retry would be equally invalid because the supposedly terminal residue could immediately change.

The accepted correction makes finish consume the supervisor and orders every timed cleanup attempt before the one non-replacing publication. Finish runs the configured initial attempt and, only when it remains indeterminate, one caller-budgeted recovery attempt; it records both. Any still-retained exact process owner crosses publication only with a non-waiting fail-safe release operation. Dropping an unfinished session performs its configured attempt once and then the same non-waiting release, never ordinary supervisor defaults. Cleanup and publication outcomes remain independently reportable.

Phase 15 completion review invalidated treating `wait_for_state` as one ordinary compiled request while hiding its repeated `read_ui_state` protocol requests. That approach proved only a three-digit request id, could outlive the remaining total-runtime deadline, issued a zero-budget poll, and discarded every poll identity from evidence. It also left aggregate timeout feasibility and the maximum expanded wire-request count unknown at launch.

Operator approved the corrected expansion contract. The configured request maximum counts logical plan operations; compilation separately derives and caps the worst-case expanded wire-request count, rejects summed worst-case operation budgets beyond total runtime, and qualifies frames with the largest possible post-handshake request id. Runtime waits preserve the earliest normalized-wait, effective-request, and remaining-run absolute deadline through transport, check it before every poll, and retain the latest completed state on timeout. Schema-v4 evidence records the exact contiguous first id, last id, and count for each logical operation, preserving all wait-poll attribution without an identity vector.

Completion review also invalidated demanding a CLI launch-none oversized-frame case. The complete request-plan file is capped at the same 262,144-byte value as a wire frame, its outer JSON contains more structure than one wire operation, and accepted operation payloads are stricter still: the largest text is 16,384 bytes and other strings are smaller. No public plan can therefore pass semantic validation yet overflow a frame. Operator approved keeping preflight frame qualification, proving exact frame rejection at the compiler/protocol layer, and using CLI launch-none coverage only for publicly expressible plan-size and semantic-payload violations. A synthetic CLI bypass or weakened product bound is not permitted.

Phase 16 preflight initially treated the lack of a path-valued app-server argument on `beryl-acceptance` as an exact-target selection blocker. That was the wrong requirement: `beryl-acceptance --executable` correctly selects the frozen Beryl diagnostic executable, while production Host Windows discovery intentionally resolves `codex` through inherited PATH. Operator confirmed that tests and project authority must not hardcode a machine-specific Codex path. The accepted live-fixture boundary therefore checks that the ordinary PATH-resolved `codex --version` reports the targeted release immediately before launch, without creating an alias, rewriting PATH, or adding an exact-program configuration surface.

The same preflight corrected the restart procedure: one acceptance session owns exactly one Beryl process until terminal cleanup and cannot restart it from inside its static request plan. Lifecycle completion and restart recovery require two serialized sessions over the same isolated home and execution workspace, with distinct non-overwriting evidence files and verified reclamation between them. No in-session restart workaround is permitted.

The first Phase 16 harness execution then demonstrated that a successful CLI exit qualifies request transport, evidence publication, and cleanup, not feature semantics. Bounded startup discovery remained in `opening` past the first ten-second `ready` window because its own thread-list request reached the configured deadline. `wait_for_state` correctly returned a structured `status = timeout` response, and the following `start_turn` correctly returned `status = not_ready`; both were transported successfully, so the static plan continued and the CLI exited zero after publishing evidence. No root turn, marker, or phase child existed. A feature acceptance plan must provide enough sequential bounded readiness windows for realistic startup and must inspect each response body for the expected matched or accepted status before qualifying the run. Treating process exit zero as lifecycle success is invalid.

The next fixture invalidated using a durable marker while leaving Phase 1 marked `wip` in authoritative `doc/plan.md`. Exact rollouts proved Beryl created direct-root siblings correctly and every extra child explicitly requested `phase_continue_new_thread`; no `plan_complete` call was misapplied. Later models followed the still-active Phase 1 status and recreated the marker without checking its precondition. The corrected fixture mirrors production continuity: child 1 durably marks Phase 1 finished and Phase 2 active in `doc/plan.md` before yielding, so child 2 derives final completion from authoritative plan state rather than a weaker side-file condition.

The first recovery session then invalidated reusing the fresh-workspace acceptance launch shape for restart proof. `beryl-acceptance` always supplied the required execution workspace through `--host-path`; on the existing isolated home, Beryl registered the same canonical path as new workspace `untitled-2` instead of reopening persisted `untitled-1`. The session remained on `pending_new_thread`, so it did not exercise exact active-thread recovery. Recovery acceptance needs an explicit existing-home launch mode that omits fresh host-workspace creation while retaining the persisted home, evidence attribution, bounded request plan, and exact process-tree ownership. Switching after startup, hand-editing REDB, or treating the duplicate workspace as recovered is invalid.
