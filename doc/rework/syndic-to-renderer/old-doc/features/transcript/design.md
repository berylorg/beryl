# Goals

Render backend-owned Codex conversation history as a responsive parent conversation narrative with Markdown semantics, selection, quoting, images, context menus, and bounded history loading.

## Non-goals

- Rendering operational activity, tool logs, command output, or subagent transcripts as transcript rows.
- Treating backend transcript history as GUI-owned durable state.
- Interpreting raw HTML as live UI content.
- Making Markdown image file bytes durable Beryl attachments.

# Decisions

## Transcript Model

- The transcript is the stable parent conversation narrative for the active backend thread.
- It shows ordered user input fragments plus parent assistant narrative items, including parent commentary, final answers, and optional parent-turn reasoning summaries when exposed by the backend.
- It excludes asynchronous or operational activity that is not parent narrative, including command execution records and output, file-change records, tool or MCP calls, subagent transcripts, title-generation maintenance turns, raw backend lifecycle notifications, status updates, and token-usage updates.
- Native app-server generated-image media output is assistant-produced transcript content and may render inline.
- Multiple user input fragments in one backend turn render as distinct user blocks rather than one merged prompt.
- Historical user-message content boundaries and item order exposed by the backend are preserved.
- User input fragments containing images preserve relative order between text and image markers. Transcript image markers are compact read-only atoms such as `[A]`.
- Backend conversation history remains backend-owned. Loaded transcript pages are transient presentation data.

## History Loading And Rendering Bounds

- Existing backend histories are loaded as bounded pages of turns, but user-visible transcript rows are backed only by resident full-detail turn data.
- Opening an existing thread prepares a coherent initial resident transcript seed before the selected transcript is published. That seed starts with the default tail turn when the turn satisfies the resident turn-data budget, or with that turn's explicit oversized-turn fallback when it does not. The seed is not required to already satisfy the full viewport-height margin before first publication.
- Startup and workspace-open paths that restore a selected existing thread use the same coherent-tail activation contract as explicit existing-thread activation. When Beryl enters the state where the workspace is loaded and open, the selected transcript viewport must already render coherent resident content or a terminal resident-budget fallback rather than transcript-local loading detail rows.
- Pending activation of an existing thread does not replace, blank, or overlay the transcript with a full-region pending/loading state. The previous coherent transcript projection remains visible until the newly prepared resident tail seed and initial viewport are ready to apply atomically; activation progress belongs in chrome, status, or localized notices.
- Applying resident history for selected-thread activation also applies the transcript's initial viewport state atomically. Existing-thread activation opens at the tail of the coherent resident seed unless a future feature defines a different explicit activation viewport policy. Render, prepaint, deferred, and post-frame callbacks must not install activation-owned scroll positions after the newly activated transcript has first rendered.
- The resident transcript window and rendered transcript frame are separate. The resident window owns full-detail turn data retained for scrolling, pins, and current viewport needs; each render frame builds UI only from the visible viewport plus bounded render overscan. Very large turns contribute semantic streamed chunk segments to the rendered frame instead of continuous row-interior pixel geometry.
- A resident transcript row is activation-publishable when its full-detail turn data and row presentation model are available for the coherent resident seed. Markdown parsing, Markdown-derived media discovery, media resource readiness, and viewport-margin saturation are not selected-thread publication gates; they are budgeted post-publication admission or expansion work that must render stable text, placeholders, or terminal fallbacks without creating fake transcript rows or scroll holes.
- Source-backed generated-image readiness is a Beryl-owned admission and lease state over a `gpui`-owned decoded/uploaded rendering resource. Beryl does not need to retain durable file bytes for saved-path-backed images. A row that contains source-backed media may be selected with stable media placeholder state, and the media coordinator later replaces only the row-owned media surface when the rendering resource is ready for that row's planned size or a terminal fallback is known.
- Transcript render inputs are cheap frame snapshots. Building a transcript render snapshot must not compute residency totals, retained-state summaries, Markdown/media plans, or other values by scanning full resident or indexed history.
- Transcript scroll-frame work must not clone, scan, parse, or retain widget state for the whole resident or indexed history.
- Offscreen pages, turn metadata, measurement hints, and cost estimates may remain in bounded caches, but cache retention must not make ordinary scroll frames process all resident or indexed history or expose unloaded transcript content as scrollable narrative.
- For the current CAS target contract, history index reads and full-detail reads both use `thread/turns/list` with `itemsView`. Beryl may use `itemsView = "notLoaded"` only for non-rendered history indexing, cursor discovery, cost-neutral turn identity, and load planning. Beryl must not render `itemsView = "notLoaded"` turns as transcript rows.
- Historical full-detail turn data uses `thread/turns/list` with `itemsView = "full"` and the smallest known history-page request that can satisfy the selected residency request. No separate per-turn item-list method is part of the supported transcript contract for this CAS target.
- Active live parent-turn source is fully resident while the turn is active, because Beryl has no supported partial active-turn reload path before CAS reports the turn as terminal. This is an active-turn source pin, not permission to fully render the turn. The active live turn uses the same streamed chunk rendering and render-budget fallbacks as historical resident turns.
- Active live parent-turn source has a separate hard retained-source safety cap for backend or model pathologies. If that cap is exceeded before terminal completion, Beryl publishes a stable local active-turn memory-budget fallback for the affected turn state and stops accumulating unbounded transcript presentation data for that active turn. This fallback is explicit Beryl UI state rather than assistant-authored content.
- After CAS reports a live parent turn as terminal and reloadable through the historical turn contract, the active-turn source pin is removed and the turn becomes ordinary historical resident data subject to the transcript residency policy.
- A full-page detail response may return more turns than the resident policy currently needs. Beryl may populate returned turns that are inside the current resident window or independently pinned, but returned turns outside those bounds must not become resident full-detail turns merely because the backend returned them.
- Beryl must never blindly load all turns of a thread into resident GUI state. Selected-thread activation, scroll-boundary loading, page restoration, and startup restore must all pass through the transcript residency policy so full-detail turn contents are admitted only for the current virtual residency window or explicit pins.
- The transcript residency controller owns loading, release, scroll-boundary extension, and retention decisions for historical full-detail turn data. Renderer, prepaint, deferred, post-frame, Markdown parser, media preload, status-line, and scrollbar callbacks for surfaces that still render scrollbars may report measurements or viewport facts, but they must not independently schedule resident history loads or release resident turns.
- The residency controller is driven by a configurable transcript residency policy rather than hardcoded row or screen counts. The policy may express leading and trailing margins in viewport-height units, cold-release hysteresis margins, maximum resident byte budgets, maximum resident turn budgets, in-flight request limits, and request-priority strategy.
- Transcript residency decisions operate at whole-turn granularity. Opening or extending a resident window loads full-detail turns in policy order, admits only turns that satisfy the resident turn-data budget, then uses measured rendered row heights for ordinary rows and streamed-chunk viewport fill facts for huge rows to decide whether the resident viewport runway has reached the configured viewport-height margin. Selected-thread activation may publish the coherent tail seed before the full margin is known; after the first GPUI layout reports row or streamed-chunk fill facts, the residency controller expands the resident window until the policy margin is satisfied or a budget, backend, or latency limit is reached. A turn that fits the resident turn-data budget remains one chronological resident turn even when the renderer later splits its presentation work into smaller render chunks.
- The residency policy's margin and budget goals are elastic. Beryl may grow the resident window when the viewport margin target is not satisfied and resource budget remains, and must shrink optional leading or trailing runway when turn-count or byte budgets would be exceeded.
- The active policy's target margin is a goal, not an entitlement to exceed resource limits. If byte, turn-count, backend, or latency budgets prevent retaining the full target margin, Beryl keeps the viewport coherent with a smaller resident runway and records diagnostics that explain the limiting budget.
- Turn-data byte budgeting is coarse grained and best effort, but it is mandatory for full-detail CAS responses. Beryl must account for retained turn content as it admits response data into GUI-owned state and must not keep an oversized historical turn's real contents resident when that turn alone exceeds the configured resident turn-data budget. Active live parent turns use the separate hard active-turn source safety cap until terminal completion.
- Resident byte budgeting must account for Beryl-owned transcript data, including retained turn/item payloads, Markdown parse and render caches, syntax-highlight and code-panel projections, media presentation state, retained inline generated-image bytes, and other transcript-owned derived state. Active live source-pin bytes are tracked separately from historical resident eviction budgets while still contributing to transcript memory diagnostics. Source-backed generated images with readable saved paths should be costed by retained metadata and active rendering resources rather than by pretending Beryl owns durable file bytes.
- Historical pins may retain full historical details independently of the viewport only for explicit UI affordances such as open turn context menus, active edit targets, and loaded media menu targets. Historical pins are bounded, visible in diagnostics, and do not make offscreen rows part of ordinary viewport load priority unless the owning affordance explicitly requests a load. The active live-turn source pin is separate and follows the active-turn hard safety cap.
- Releasing full-detail data outside the resident policy must preserve backend turn identity, chronological ordering facts that are known exactly, cursor/index metadata needed to fetch history again, and the measured row heights or semantic chunk anchors needed for stable scroll-boundary behavior. Release must not leave a scrollable transcript row whose visible content is a synthetic loading message.
- If the user attempts to scroll beyond the resident full-detail boundary, Beryl clamps the scroll at the resident edge, starts or continues policy-allowed loading work for the requested direction, and extends the scrollable range only after coherent resident turns are ready. Beryl must not scroll into a nonresident, unloaded, or fake loading transcript area. Media readiness for resident rows is represented by stable row-owned media placeholders or terminal fallbacks, not by scrollable loading rows.
- Missing full-detail data is residency state, not assistant narrative content. Beryl must not represent unloaded historical details as synthetic assistant loading messages, and those states must not participate in selection, copying, quoting, context-menu targeting, Markdown parsing, or transcript media layout.
- A historical turn whose full-detail contents are terminally too large for the active resident turn-data budget may publish a stable oversized-turn fallback row at that turn's chronological position. The fallback row must preserve turn identity and make clear that the real contents were omitted because the turn exceeds Beryl's transcript memory budget; it must not masquerade as assistant-authored content, a loading state, or a partial rendering of the omitted turn.
- Resident-window admission or release, page restoration, media load/decode, Markdown layout changes, and cache release must preserve the active semantic scroll anchor or detached manual position. Anchor preservation must use explicit row identity, measured geometry, and policy-owned boundary decisions rather than raw offsets that can jump into unloaded or virtual empty space.
- Text selection and the quote popup are visible-frame affordances. When scrolling or virtualization loses stable selection geometry, the selection or quote popup closes instead of pinning offscreen historical details.
- Generated images remain source-backed when a readable `savedPath` exists, and inline generated-image bytes must not be retained after sanitization for saved-path-backed images.
- Transcript presentation rows preserve their owning backend turn identity and chronological source turn position when that position is exact. Viewport-derived status such as the status-line `View` count must use transcript-owned turn ownership metadata rather than scanning rendered text or counting presentation rows.
- Status chrome must not own transcript/history pagination. It may only consume a transcript-owned Turn View snapshot or equivalent shell-local facts derived from transcript history completeness and viewport ownership.
- If lazy history means a retained row's source position is only window-relative, Beryl must not expose that value as an exact status-line turn number. It should render `-` for the unknown side of the `View` count until exact selected-thread turn numbering is known.
- With the current CAS target contract, exact selected-thread totals before complete transcript history ownership require a backend exact-total field. Beryl must not page through history solely to improve the status-line `View` count.
- Transcript residency and rendering diagnostics are content-free and bounded. They should include policy parameters, resident turn count, active-turn source-pin state, active-turn retained-source byte estimate, rendered row count, visible range, desired and actual margins, estimated resident bytes by category, estimated render cost by category, in-flight request count, skipped/released counts, clamp events, large-turn chunk counts, streamed anchor chunk identity, rendered chunk range, streamed fill direction, chunk-window computation time, and resident-budget, active-turn source-budget, or render-budget fallback reasons without logging transcript text, paths, or secrets.
- Residency counters consumed by ordinary render frames are maintained incrementally when residency state changes. Full retained-state scans are explicit diagnostic-tool work only and must not be part of transcript render, prepaint, scroll, scrollbar, media-preload, status-line, or frame-metric callbacks.

## Render Hot Path And Preload Architecture

- Transcript rendering uses variable-height virtualization for ordinary transcript rows because row height depends on Markdown, media, code panels, and selection geometry. Huge-turn interiors use semantic chunk streaming instead of continuous pixel virtualization.
- Row virtualization is necessary but not sufficient. A visible transcript row may be large, so visible-row render work must consume precomputed row presentation models whenever stable source data already exists, and huge-turn render work must consume precomputed chunk presentation models around a semantic chunk anchor.
- A transcript row presentation model is derived from resident turn data, stream projection state, Markdown keys, media references, code-panel ids, copy-source spans, stable row identity, item counts, text counts, and revision metadata outside the ordinary render hot path.
- Row rendering may construct GPUI elements for visible rows and bounded render overscan, but it must not rediscover turn block structure, search whole turn item lists repeatedly, format stable ids repeatedly, schedule resident history loads, or parse Markdown/media runs as part of ordinary frame construction.
- Row measurement caches are keyed by row identity, row presentation revision, transcript width, theme/font revision, and any layout-affecting display state. Cache invalidation must be explicit and must preserve semantic scroll anchors when ordinary measured row heights change.
- Very large resident turns require streamed chunk presentation. If a single admitted turn can exceed smooth debug-build rendering budgets, Beryl splits the derived row work into stable Markdown-safe render chunks while preserving one visible turn identity, chronological item order, copy source for rendered chunks, context-menu targeting, and media ownership. Active live turns use this same render path even though their source remains fully pinned while active.
- Large-turn detection, chunk sizing, and render admission may use a checked-in render-cost model with empirical weights for source or presentation facts such as item counts, Markdown block counts, line counts, text bytes, media counts, code-panel counts, code text size, and inline span counts. These weights are render-budget inputs only; they must not decide which visible content can be omitted and must not define scroll spacer geometry.
- Normal builds use deterministic checked-in render-cost weights. Calibration may be an explicit benchmark or developer tool that reports or updates those weights under operator control, but ordinary builds must not benchmark the local machine, rewrite source, or make runtime weight management part of transcript rendering.
- Render chunks are capped by presentation render cost rather than by guessed pixel height. A normal resident turn contributes one whole-row segment to the rendered transcript frame. A large resident turn contributes streamed chunk segments around the frame anchor or frame expansion direction until the viewport plus bounded render overscan is full, the turn boundary is reached, a resident boundary is reached, or an explicit render-budget fallback is required.
- Streamed huge-turn mode abandons continuous pixel geometry inside the turn. Unrendered offscreen chunks have no spacer geometry, no cumulative offset, and no scrollbar extent. Measured heights for rendered chunks may be used only for current-frame viewport fill, local anchor placement, and deciding whether another adjacent chunk is needed.
- The transcript viewport owns a rendered-frame model that spans ordinary rows and streamed chunks together. A frame records the visible and overscan content segments above and below one semantic anchor, each segment's stable turn or chunk identity, and measured heights only for segments that were actually rendered. The frame is the input to wheel, touchpad, selection visibility, diagnostics, and residency fill facts; individual row renderers report segment measurements but do not independently own transcript navigation.
- Continuous wheel and touchpad input is delta-preserving. When a user scrolls by a small pixel delta, Beryl first consumes that delta inside the current rendered frame. If the delta crosses a frame edge, Beryl prepends or appends the adjacent resident row or streamed chunk in the requested direction, keeps the same visual anchor, and applies any remaining delta against the expanded frame. Continuous scroll must not convert a boundary crossing into a semantic row or chunk placement jump.
- Semantic placement inside one transcript history is reserved for explicit jump commands. Current exposed jump commands are focused `Ctrl+Up` and `Ctrl+Down` turn-to-turn navigation. Future explicit head or tail jump commands may also use semantic placement. Wheel or touchpad scrolling must not call row-to-top or row-to-bottom placement helpers merely because the next content segment belongs to a different turn or chunk.
- Unknown offscreen chunk geometry must stay unknown. Beryl must not create blank top or bottom spacers from measured or guessed chunk ranges, must not use render-cost weights as visual-height estimates, and must not expose unrendered chunk ranges as scrollable empty space.
- Render-budget fallbacks are distinct from resident-budget fallbacks. A turn that fits resident turn-data budgeting but contains a chunk that cannot be safely rendered within the render budget publishes a stable row-owned render-budget fallback at that chunk's semantic position. A turn that exceeds resident turn-data budgeting publishes the oversized-turn fallback instead of retaining the real contents. This phase does not expose a render-anyway or force-render control.
- Transcript media readiness is owned by a budgeted admission coordinator, not by prepaint. Render or prepaint may report visible and desired preload ranges, stable row identities, viewport size, and layout facts, but the coordinator owns coalescing, time budgets, row budgets, byte budgets, media decode/upload limits, cancellation, stale-result rejection, and presentability decisions.
- Markdown media-run segmentation used for admission or speculative preload is cached by stable Markdown key, source revision, and parsing revision. Admission and preload must reuse that cache or schedule bounded off-render work instead of re-segmenting offscreen Markdown during prepaint.
- Missing media readiness or Markdown-derived media plans are admission state for historical and completed resident rows. They must not create skeleton transcript rows, fake loading messages, scrollable unloaded areas, or renderer-owned prerequisites for selected-thread publication. Rows may expose stable row-owned media placeholders while the coordinator resolves media readiness, and later updates must be scoped to those media surfaces rather than replacing transcript rows or activation-owned viewport state.
- Beryl may use bounded offscreen measurement or resource preparation for individual staged rows or media items, but offscreen rendering is not a substitute for residency admission or selected-thread activation. Offscreen work must obey the same row, byte, time, in-flight, and stale-result budgets as media admission, and must not render an unbounded history window or retain resources for nonresident rows.
- Speculative preload may prepare future resident rows, but it is not a render-path substitute for admission. A row that is already visible consumes settled media descriptors and must not initiate readiness work as part of ordinary frame construction.
- Code-panel interaction state inside transcript rows is keyed by typed ownership that includes the transcript row identity and a local panel identity. Pruning visible code-panel state must retain or release row-owned state by row identity rather than scanning panel id strings against every visible row.
- Transcript frame metrics are measured around all transcript-render work they claim to represent, including snapshot construction and render-adjacent pruning. Metrics must remain content-free and bounded.

## Markdown And Code

- Transcript Markdown is parsed into Beryl-owned semantic block and inline structures before rendering.
- Supported Markdown semantics include paragraphs, headings, unordered and ordered lists, block quotes, inline code spans, fenced code blocks, links, images, explicit line breaks, thematic breaks, emphasis, strong emphasis, and math spans or blocks.
- Unsupported or non-Markdown conventions render literally unless represented by the transcript Markdown model.
- Raw HTML is represented as literal source or unsupported source and must never be interpreted as executable or styled HTML.
- Fenced code blocks render through the shared code panel widget.
- Syntax highlighting is presentation derived from preserved source text and optional language labels. It must not replace backend-owned transcript text, Markdown copy source, or code-panel copy source.
- Parser output assigns token roles to source ranges; rendering maps token roles through application appearance settings.
- The Markdown language is a registered syntax-highlighting language. Unsupported, unknown, empty, partial, or invalid labels render as plain text while preserving source and selection semantics.
- `beryl-theme` fenced code blocks remain ordinary transcript content, with theme-specific actions owned by `doc/features/theming/design.md`.
- If an agent turn produces a non-image file artifact that exists on the local filesystem, the GUI represents that artifact as a clickable file link and asks the operating system to open it with the default associated application.
- Markdown links using the Beryl-owned `beryl_threadid://<percent-encoded-thread-id>` scheme are internal transcript thread links. Activating one requests exact conversation-thread activation through the conversation-threads feature and must not ask the operating system to open a URL.
- Transcript thread-link activation is user-initiated thread navigation. Successful activation contributes to the workspace-local thread navigation history defined by `doc/features/conversation-threads/design.md`.
- Unknown, malformed, empty, unregistered, out-of-scope, or rebind-required transcript thread links fail with bounded Beryl UI notice behavior and leave the active thread unchanged.

## Transcript Images And Media

- Transcript image markers derived from Beryl-submitted local images remain compact atomic labels in user blocks. Activating a marker opens Beryl's preview popup when durable image bytes are available.
- Historical image markers remain visible even if their image bytes cannot be recovered; unavailable preview state is reported without replacing the marker with plain text.
- Native app-server generated-image output renders as transcript media. A live backend item whose generation is genuinely pending may show a stable pending placeholder. A historical or completed generated-image item may publish as part of a coherent resident row with a stable media placeholder, and its media surface becomes fully rendered only after embedded bytes, a readable saved path, or a terminal fallback state is ready.
- A generated-image saved path is the authoritative generated image artifact while readable. Beryl may retain bounded presentation state but must not create a Beryl-side durable copy solely to preserve generated images when the saved path becomes unreadable.
- Markdown image syntax with a local filesystem target is a transcript media request. Relative paths resolve against the conversation thread's recorded execution target, not the GUI process working directory.
- File bytes referenced by Markdown remain filesystem state and may disappear or change outside Beryl. Beryl renders unavailable or updated filesystem state honestly rather than treating the Markdown reference as an attached artifact.
- Absolute Markdown image targets render only when proven to belong to the selected thread's expected runtime/member boundary.
- Supported raster image targets render in place. SVG and other non-raster formats are unsupported in this phase unless a later design expands support.
- Unsupported targets render `<alt> (render not supported)`. Missing or unreadable targets render `<alt> (file unavailable)`. Path-policy rejections render `<alt> (path not allowed)`. Size-admission rejections render `<alt> (image too large)`.
- Ordinary Markdown links remain links, including linked images shaped as `[![alt](path)](target)`.
- Consecutive transcript media items form media runs. One item occupies a full row, uses padded transcript content width, is capped by natural raster size, and is centered when narrower than the row.
- Multi-item runs use a shared compact width derived from about 30 `M` glyph advances in the active regular conversation text font, capped per item by natural size, and wrap at the right edge.
- Consecutive Markdown image embeds separated only by Markdown whitespace or line breaks are extracted into media rows even when their paragraph has surrounding prose.
- Activating a loaded item in a multi-item run toggles UI-local promotion for that item. Promotion gives it a single-image row at its transcript position while non-promoted siblings remain compact before or after it.
- Media promotion is presentation state only. It must not mutate backend history, Markdown source, generated-image records, media cache ownership, selection semantics, or workspace persistence.
- Secondary-clicking a resident transcript media item opens the owning turn context menu plus `Copy image` and `Save image as` for that item.
- Media image actions derive full-resolution bytes from the authoritative file-backed or byte-backed source at action time, not from retained preview pixels.
- Pending placeholders, unsupported fallbacks, unavailable files, and path-rejected fallbacks do not expose image-specific actions.
- Completed transcript media may initially expose a stable row-owned media placeholder while loading, decoding, or resource admission is still pending. That placeholder belongs to an already-published resident row; it must not block selected-thread publication, create a fake transcript row, or overwrite activation-owned viewport state. When readiness resolves, Beryl updates only that media surface to the loaded image or a terminal fallback.

## Selection, Copying, And Quote Harvesting

- Rendered transcript text supports ordinary desktop text selection for clipboard copying.
- Selection, scrolling, live remeasurement, and viewport virtualization preserve logical selected text while selected content remains in the resident transcript window.
- In streamed huge-turn mode, transcript text selection, quote harvesting, and Markdown-preserving copy are limited to currently rendered chunks. Selection does not span through unrendered chunks. Dedicated code-panel copy actions remain available for rendered code panels and use their own source text.
- Visible highlight rectangles must match the rendered portions of the logical selection, including soft-wrapped start and end positions.
- Beryl-owned Markdown semantic structures retain source-span or copy-source information so selection can produce Markdown-preserving copied text without reparsing full transcript history.
- Standard copy commands write Markdown-preserving selected text to the system clipboard, not lossy rendered-only text.
- Copying preserves Markdown syntax for inline code, emphasis, strong emphasis, links, lists, block quotes, headings, code blocks, image markers, math, and unsupported source fallbacks.
- Selected transcript image markers copy as explanatory text such as `[Image A]`.
- Selecting across a Markdown code block copies that selection as Markdown code-block source. A code block's own copy action copies only bare code.
- Selecting non-empty transcript text shows a transcript quote popup near the selection.
- The quote popup initially contains `Quote`, which inserts selected Markdown-preserving text into the current draft as Markdown block quote text by prefixing each logical line with `> `.
- Visual soft wrapping does not create additional quoted lines.
- Quote insertion uses the latest remembered draft insertion point or appends to the draft when no insertion point is known.
- After quote insertion, the remembered insertion point moves after the inserted quote block so repeated quote actions gather passages in reading order.
- Quote insertion preserves transcript scroll position, does not force focus into the composer, and does not mutate the clipboard.
- The quote popup closes when selection clears, outside click, `Escape`, transcript scrolling or virtualization loses stable selection geometry, or after accepted quote action.

## Turn Context Menu And Edit Presentation

- When no transcript selection is active, secondary-clicking rendered content that maps to one resident parent turn opens that turn's context menu.
- The turn context menu targets the whole parent turn owning the clicked area, whether the click lands on user input or assistant narrative.
- The menu always contains `Edit message` for resident full-detail turn rows and disables it with a specific unavailable-reason tooltip when editing cannot currently start.
- The menu contains `Branch and switch to` and `Branch in background` only when branch actions are available. Branch/edit orchestration is owned by the conversation-threads feature.
- The menu contains `Update thread title` for resident parent turns when the clicked turn can provide a title seed for the selected thread. When title update cannot currently start, the row remains visible for eligible turn rows and is disabled with a specific unavailable-reason tooltip. Title-update orchestration is owned by the conversation-threads feature.
- When opened from resident transcript media, the same menu is augmented with media-specific image actions for the clicked item.
- The menu is not opened for empty transcript space, operational activity, the activity caret, or active transcript selections.
- While thread-edit mode is active, the targeted turn and all later loaded turns render dimmed. Rows remain selectable, copyable, quoteable, and scrollable until commit removes them from backend history.
- Active-thread changes, workspace changes, loss of stable target turn, selected-thread activation, active turn, or selected-thread compaction cancel edit mode without mutating the composer draft.

## Scrolling And Activity Caret

- The transcript region does not render a visual scrollbar. Transcript navigation is owned by wheel, touchpad, keyboard, turn-level semantic navigation commands, live-turn autoscroll policy, and selected-thread activation policy. Future navigation affordances may be added without restoring continuous pixel geometry for huge-turn interiors, but this phase does not expose page-wise or dedicated chunk-to-chunk navigation commands.
- Wheel and touchpad input first scroll within the currently rendered transcript frame when local rendered geometry permits it. When navigation reaches a rendered frame edge, Beryl advances the frame by adjacent resident content in the requested direction, which may be an ordinary turn row, a streamed chunk in the same turn, or a streamed chunk in an adjacent turn. The visual anchor and remaining scroll delta are preserved across that expansion, so crossing from one turn or chunk into another does not jump to a top, bottom, or default placement.
- Focused `Ctrl+Up` and `Ctrl+Down` turn-to-turn navigation commands target previous or next backend turns, not individual chunks. When the target turn is huge, Beryl anchors that turn at the requested boundary and streams chunks from there.
- Transcript live-turn scroll behavior is a forward-only per-turn state machine. Automatic phases may advance from accepted prompt anchoring to commentary following to final-response anchoring, but they must not move backward, repeat a completed phase, or issue competing viewport corrections in quick succession.
- Live-tail following may shift the viewport incrementally as new text is appended while autoscroll is active. This is an automatic follow behavior, not a same-transcript jump command, and manual wheel or touchpad input must detach it.
- When a new user-authored turn input fragment is accepted as the start of a new reading cycle, the transcript viewport positions the latest accepted prompt fragment for rereading. If the fragment fits with reserved response runway, its start is anchored at the top of the transcript region. If the fragment is taller than the available prompt area, the viewport shows the latest visual prompt lines or measured prompt-block tail that fit, while preserving a small virtual runway below for upcoming assistant narrative when the viewport is large enough.
- The reserved response runway is virtual scroll geometry, not transcript content. It must be bounded by the transcript viewport, clamp away on very small viewports, and must not create copyable, selectable, or durable transcript rows.
- While parent assistant narrative commentary is arriving and the user has not manually scrolled, Beryl keeps the prompt-reread anchor and its virtual response runway while commentary still fits below that prompt anchor. Commentary arrival alone must not collapse the runway or move the prompt downward. Beryl may enter commentary following only after measured commentary growth would overflow the viewport below the prompt anchor, and then only as needed to keep newly arriving commentary visible at the bottom of the viewport. Commentary following preserves the current semantic follow target rather than repeatedly bottom-aligning the whole turn.
- When the first stable final-answer content for the active turn becomes available and the user has not manually scrolled, Beryl anchors the start of that final response near the top edge of the transcript viewport exactly once, with enough top-edge paint guard to keep the first line fully visible rather than clipped by the viewport mask. The guard is derived from the measured first rendered final-answer line height, with a small minimum floor for ordinary font sizes, so transcript font-size or theme changes scale the protected top edge instead of relying on a fixed pixel constant.
- After final-response anchoring, final content grows downward and overflows below the viewport without automatic following. Beryl may retain bounded virtual scroll slack while the final response is shorter than the viewport so the final-start offset remains representable, but it must not reissue final-start scrolling after the one-time anchor. Turn completion must not bottom-align the end of the final response or the end of turn output.
- Final-read may adjust the raw row offset only to preserve the same semantic final-answer start when content above that start remeasures, such as media loading, Markdown layout changes, or resident-window geometry changes. This correction preserves the original final-start anchor; it is not commentary following, final growth following, or turn-end bottom alignment.
- Transcript anchor geometry must match the rendered text role and rendered container width. User prompt fragments measure Markdown inside the prompt card content width; assistant commentary, reasoning, and final-answer Markdown measure inside the row narrative content width. These widths must not be conflated because wrapping above the final answer changes the semantic final-start offset.
- Live prompt and final-response anchors must remain representable when surrounding UI changes the transcript viewport height. If the activity panel, composer, image paste UI, or other non-transcript chrome changes height while a live anchor owns the viewport, Beryl extends bounded virtual slack for that frame instead of pulling earlier transcript rows above the anchor to fill the newly available space.
- If the backend turn ends without stable final-answer content, Beryl does not synthesize a final-response anchor and does not install a completion-time bottom alignment.
- If parent commentary arrives after final-response anchoring, it must not steal the viewport from the final-response reading position.
- Active-turn steering input is not a new reading cycle. Rendering an accepted steering fragment must preserve the current transcript scroll state, whether that state is commentary following, final-response reading, detached manual scroll, or another phase.
- If the user manually scrolls during or after a live turn, Beryl enters a detached manual-scroll state for that turn. Detached state suppresses later automatic prompt, commentary, and final-response viewport changes until the next new user-authored turn input starts a new reading cycle.
- Manual scroll intent from wheel, touchpad, page, keyboard, or semantic transcript navigation releases live-turn anchoring before range-dependent transcript residency work runs, even if the navigation event is later dropped, clamped, or delayed by reset/remeasurement.
- Detached manual-scroll state retains bounded virtual trailing runway for the strongest reading anchor from that reading cycle. Before stable final-answer content exists, the retained anchor is the latest user-authored prompt fragment so the user can manually scroll that prompt into the prompt-reread position. Once stable final-answer content exists, the retained anchor is the final-answer start so the user can manually scroll the first final-response line to the same measured, guarded top position that automatic final-start anchoring used. This retained runway is a non-scrolling affordance only; it must not reissue prompt-reread scrolling, commentary following, final-start anchoring, final-growth following, or turn-completion bottom alignment.
- When the transcript viewport bottom is within virtual trailing runway or slack, viewport-derived turn status treats the viewport as looking at the final backend turn if at least one exact turn is known. Virtual trailing geometry is not transcript content and must not create a synthetic current turn.
- Live row remeasurement, Markdown layout changes, media load/decode, resident-window changes, and history-page restoration must preserve the active semantic scroll anchor or detached manual position. Residency updates may preserve the previous content-anchor row and offset for the affected anchor row, but they must not scroll any merely visible row to its top or fall back to raw offsets that can jump into unloaded or virtual empty space or cause visible oscillation.
- Existing-thread activation without a live-turn anchor opens at the real end of the prepared resident window as its one selected-thread-activation viewport decision and does not synthesize live-turn response runway for already-resident user input fragments.
- If the latest resident history turn already contains stable final-answer content, selected-thread activation may expose passive bounded virtual trailing runway for that final-answer start. This resident-history runway uses the same measured final-answer top guard as active final-read placement. It is a manual scroll affordance only: it must not move the activation viewport away from the real tail, reissue final-start anchoring, follow final growth, or use deferred renderer callbacks.
- Live-turn anchoring is distinct from selected-thread activation. It belongs to accepted new user-authored turns and active response streaming, not to renderer-installed passive anchors that change the selected-thread activation viewport after first paint.
- While the selected thread has an active parent turn, the transcript renders a non-interactive block activity caret at the end of the parent conversation narrative.
- The activity caret is not transcript content, Markdown source, selectable text, copyable text, quoteable text, or draft-caret state.
- The caret has stable geometry while blinking, does not cause reflow, disappears when the parent turn stops working, and follows platform text-caret blink policy when available. When blinking is disabled or reduced-motion requests apply, it renders steadily.
